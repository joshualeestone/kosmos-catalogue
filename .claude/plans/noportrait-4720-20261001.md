# noportrait-4720: publish a catalogue that names no portraits, until Kosmos can use them

Asked by Splinter, 2026-10-01 08:51 (priority). Baron measured that the published catalogue (serial
1790810974) sets avatar.image on all 355 members, and no SERVED Kosmos reads /api/catalogue/portrait yet.
A served build's team step (tcPortrait) fetches avatar.image as a path on its own board, which does not
serve it, so every made team member gets no picture and a "portrait could not be set" row. Baron's fix
is kosmos#4720; until it ships, publish what the served builds handled before #10: no avatar.image.

## Change
- build.js: `PUBLISH_PORTRAITS = false`. Portraits are still checked (a bad file is still refused), but
  every member's avatar.image and imageSha256 are null, so main() copies no portrait into dist/ and
  check-deploy expects none. `build({portraits})` and `main(argv, {portraits})` override it, so the
  publishing path stays tested.
- Turning it back on is a one-line commit after the Kosmos release with #4720 is served.

## Why null is the old behaviour (read on kosmos origin/main 49c0c076f)
- engine/teamseed.js:259 passes `image: null` when avatar.image is not a non-empty string.
- web/index.html tcPortrait: no image -> draws the generated mark for the member's name and PUTs it, the
  same picture a single agent gets. With an image it fetches '/'+path, which an old board 404s -> 'failed'.

## Tests
- New: with the switch off, no member names a portrait (CONTROL: the same tree with portraits on names
  one), and a bad portrait is still refused. Flipping the switch to true fails it (measured).
- main(): writes no avatars/ while off; with {portraits: true} copies the file (kept arm).
- Full suite 105/105; a real build: 355 members, 0 with image or hash, dist holds only catalogue.json.

## Weakest premise
That every SERVED build (prod 0.7.11, staging 0.7.15) treats a null avatar.image like origin/main does. The
null path predates the portraits (catalogue #10 is what first set it), so builds made before #10 only ever
saw null. Not measured on a served bundle.

## Measured after the plan (closes the weakest premise for staging)
- Served staging 0.7.15 (tarball sha matches latest-staging.json): no engine/teamseed.js and no tcPortrait,
  so it makes no teams; its engine/catalogue.js uses a portrait only when imageSha256 is a string. Null is
  safe there. The team step with the bug is on main (the 0.7.16 cut), where null draws the generated mark.
